# Большие данные: потоковый анализ

!!! warning "Это работает, но Fiji и napari — не то место, откуда этим управлять"
    Для **изображений, которые помещаются в память (примерно 1–2 ГБ)**,
    продолжайте пользоваться обычным интерактивным путём: выберите
    изображение, нажмите **OK**, получите результат. Ничего с этой страницы
    для этого не нужно.

    С поблочной потоковой обработкой (OME-Zarr) скрипт Wavu может
    обработать данные **до примерно 50 ГБ на локальном компьютере**. Но Fiji
    и napari — просмотрщики с холстом, рассчитанные на данные в памяти: во
    время потока они видят лишь **небольшой предпросмотр или итоговый
    результат**, остаются медленными, пока он идёт, и **не являются
    рекомендуемым местом, чтобы им управлять**. Свыше ~50 ГБ используйте
    вместо этого пакетный или HPC-конвейер (см.
    [конец этой страницы](#when-not-to-do-this-in-fiji-or-napari)).

!!! info "Шаблон проектирования, а не встроенная функция"
    Всё, что ниже, — это то, как **вы** пишете **свой собственный скрипт**.
    Сам Wavu лишь передаёт в `run` путь и параметры и возвращает путь,
    который отдаёт ваш скрипт. Блоки, dask и OME-Zarr — дело вашего скрипта,
    а его пакеты живут в его собственном `pixi.toml`.

## Идея простыми словами

![Большой сырой 3-D блок на разделочной доске ножом нарезается на восемь кусков; куски параллельно отправляются на четыре маленькие подкухни, каждая готовит по одному куску за раз; готовые куски собираются на одной тарелке в законченное блюдо, которое светится, когда оно готово.](../assets/img/stream/sub-kitchens.svg){ width="800" }

*Большое изображение нарезается на куски (блоки OME-Zarr, chunks), и
несколько подкухонь (параллельные воркеры) готовят каждая по одному куску
за раз, так что в памяти одновременно лишь несколько кусков. Готовые куски
собираются на одной тарелке в одно блюдо: результат.*

Вернёмся в ресторан. Свадьба заказала ужин на пятьсот гостей. Ни на одном
столе все эти ингредиенты не поместятся, поэтому кухня работает
**партиями**: она приносит ингредиенты **ящик за ящиком**, готовит
несколько ящиков сразу на разных плитах и отправляет тарелки в зал по мере
готовности. Официант приносит к вашему столу лишь **дегустационную
тарелку**, чтобы показать, что блюдо выглядит как надо.

Для изображений ящики — это **блоки** (*chunks*): большое изображение,
разрезанное на сетку маленьких блоков. Каждый блок сохраняется как **свой
собственный маленький файл**, так что программа может прочитать один блок,
не трогая остальные.

![Большое изображение разрезается на сетку блоков; каждый блок сохраняется как отдельный маленький файл в папке OME-Zarr; читатель берёт только нужные ему блоки, по одному файлу за раз, а числа, измеренные на каждом, заполняют таблицу результатов и график.](../assets/img/stream/zarr-chunking.svg){ width="800" }

*Большое изображение превращается в папку маленьких файлов, по одному на
блок. Читатель берёт только нужные ему файлы, по одному за раз, и то, что
он измеряет на каждом блоке, становится строкой таблицы результатов и
столбиком графика.*

## Почему OME-Zarr

**OME-Zarr** (его ещё называют OME-NGFF, Next-Generation File Format) —
открытый формат как раз для этого:

- **Поблочный.** Каждый блок — отдельный файл, поэтому чтение одной
  области стоит одну область, а не всё изображение.
- **Многомасштабный.** Изображение хранится также в меньших разрешениях
  (*пирамида*); просмотрщик сначала показывает маленький уровень и
  подгружает детали только там, где вы увеличиваете.
- **Дружит с облаком.** Та же структура работает в папке, на сетевом диске
  или в объектном хранилище (S3).
- **Открытый.** Стандарт сообщества OME, его читают napari, Fiji и Python.

Сравните с **одним большим TIFF**: большинство программ читают его как
один файл от начала до конца, классический TIFF упирается в 4 ГБ (BigTIFF
снимает это ограничение), и пишется он по порядку через **одного
писателя**. Для нескольких гигабайт сойдёт, для пятидесяти — мучение.

## Потоковая обработка в бэкенде

Весь фокус в том, что официант никогда не носит ингредиенты. Ваш скрипт
получает не пиксели, а **путь**.

![Одно хранилище OME-Zarr, data.ome.zarr, с входной группой /image слева и выходной группой /label справа; воркер читает по одному блоку за раз в свою маленькую коробку памяти, обрабатывает его, записывает блок результата в соответствующую ячейку /label и отпускает его; каждый блок оставляет крошечную таблицу результатов, а в конце они сливаются в одну собранную таблицу справа.](../assets/img/stream/stream-loading.svg){ width="800" }

*Одно хранилище, две группы: слева группа `/image`, справа группа
`/label`. По одному блоку за раз попадает из `/image` в маленькую коробку
памяти, обрабатывается, записывается в свою ячейку в `/label` и покидает
память. Каждый блок также оставляет маленькую таблицу результатов; в конце
они сливаются в одну собранную таблицу.*

Шаг за шагом, внутри `run`:

1. **Получите путь.** Здесь это текстовый параметр. (Путь, отправленный
   как *вход* и указывающий не на TIFF, CSV или ZIP, тоже приходит
   неоткрытым, как `pathlib.Path`; см.
   [данные при передаче](../model/architecture.md#data-on-the-wire).)
2. **Откройте его лениво.** `dask.array.from_zarr` знает форму, тип и
   сетку блоков, но ещё **не прочитал ни одного пикселя**.
3. **Обрабатывайте блок за блоком.** Вы описываете работу над всем
   массивом; dask превращает её в одну маленькую задачу на блок.
4. **Запишите результат рядом с входом**, а не в `ctx.tmpdir`, который
   удаляется, когда воркер останавливается.
5. **Верните `Path` и маленький массив предпросмотра.** Путь печатается в
   Log; предпросмотр (намного меньше лимита в 4 МиБ для встроенной
   передачи) открывается как обычное изображение.

## Параллельная обработка с dask

[dask](https://docs.dask.org/en/stable/array.html) — шеф-повар кухни: он
раздаёт ящики по плитам.

![Четыре воркера, нарисованные как вращающиеся колёса, берут каждый свой блок вместе с тонкой каймой, позаимствованной у соседей, обрабатывают их одновременно и обрезают кайму; каждый обработанный блок возвращается в выходную сетку, а его числа становятся новой строкой растущей таблицы результатов.](../assets/img/stream/parallel-processing.svg){ width="800" }

*Четыре воркера обрабатывают четыре блока одновременно. Каждый блок несёт
тонкую кайму от соседей (halo, ореол), которую потом обрезают. Каждый
результат идёт двумя путями: обработанный блок — обратно на своё место в
выходной сетке (сборка блоков), а его числа — в новую строку таблицы
результатов (сборка результатов).*

- **`map_blocks`** запускает вашу функцию на каждом блоке по отдельности:
  подходит для всего, что смотрит на один пиксель за раз, например для
  порога.
- **`map_overlap`** сначала добавляет **ореол** (halo) в `depth` пикселей,
  позаимствованных у соседних блоков, запускает вашу функцию, а затем
  обрезает ореол. Он нужен фильтрам, которые смотрят на соседей
  (гауссово размытие, медиана, морфология), иначе на каждой границе блоков
  появятся швы. `boundary="reflect"` говорит, что брать на внешнем краю
  изображения. Для гауссова фильтра достаточно `depth` около
  `4 × sigma` пикселей.

```python
import dask.array as da

image = da.from_zarr("D:/data/big.zarr", component="0")   # лениво, пока ничего не прочитано
mask = image.map_blocks(lambda block: block > 500, dtype=bool)   # соседи не нужны
```

**Размер блока.** Ориентируйтесь на **десятки МБ на блок** (например,
64 × 512 × 512 `uint16` = 32 МБ). Гораздо меньше — и dask тратит время на
учёт; гораздо больше — и каждой плите нужно много места на столе.
Используйте `image.rechunk(...)`, если блоки на диске сильно отличаются от
этого.

**Число воркеров.** Планировщик dask по умолчанию для массивов использует
**потоки** в одном процессе; они делят память, поэтому передача блоков
ничего не стоит. Сколько их, задаётся через
`dask.config.set(num_workers=4)`. Если ваша функция на чистом Python и не
ускоряется от большего числа потоков, попробуйте `scheduler="processes"`.

**Правило для памяти.** Пиковая память ≈ **воркеры × размер блока × 3–4**
(вход, ореол, копия во float, выход). Четырём воркерам на блоках по 32 МБ
нужно около половины гигабайта, каким бы большим ни было всё изображение.

## Устройство кода

Папка скрипта для потоковой обработки — обычная папка скрипта Wavu.
Добавьте пакеты в её `pixi.toml` (все есть на conda-forge):

```toml
[dependencies]
dask = ">=2024.1"
zarr = ">=2.16"
ome-zarr = ">=0.9"     # `ome-zarr` с conda-forge, импортируется как ome_zarr
scipy = ">=1.10"
tifffile = ">=2023.1"
```

`script.py`, каркас:

```python
"""Smooth a large OME-Zarr image chunk by chunk (Gaussian blur)."""
from pathlib import Path

import dask
import dask.array as da
import numpy as np
from dask.callbacks import Callback
from scipy import ndimage

PARAMS = {
    "store": {"type": "str", "default": "", "label": "Input OME-Zarr folder"},
    "sigma": {"type": "float", "default": 2.0, "label": "Sigma (pixels)"},
    "output_format": {"type": "choice", "choices": ["ome-zarr", "tiff"], "default": "ome-zarr"},
}


class WavuProgress(Callback):
    """Report dask's finished tasks as ctx.progress, and stop when the user cancels."""

    def __init__(self, ctx):
        super().__init__()
        self.ctx = ctx

    def _start_state(self, dsk, state):
        self.total = sum(len(state[k]) for k in ("ready", "waiting", "running", "finished"))

    def _posttask(self, key, result, dsk, state, worker_id):
        self.ctx.progress(len(state["finished"]) / max(self.total, 1))
        self.ctx.check_cancelled()          # выбрасывает wavu.Cancelled, что останавливает dask


def run(ctx, inputs, params):
    store = Path(params["store"])
    sigma = params["sigma"]
    image = da.from_zarr(str(store), component="0")    # полное разрешение, лениво
    ctx.log(f"{image.shape} {image.dtype}, chunks {image.chunksize}")

    depth = int(4 * sigma) + 1                         # ореол, который нужен гауссову фильтру
    smoothed = image.astype(np.float32).map_overlap(
        ndimage.gaussian_filter, depth=depth, boundary="reflect", sigma=sigma)

    with dask.config.set(scheduler="threads", num_workers=4):
        if params["output_format"] == "ome-zarr":
            out = store.with_name(store.stem + "-smoothed.zarr")
            write_ome_zarr(smoothed, out, ctx)
        else:
            out = store.with_name(store.stem + "-smoothed.tif")
            write_tiff(smoothed, out, ctx)

        z = smoothed.shape[0] // 2                     # предпросмотр: средняя плоскость, уменьшенная
        step = max(1, max(smoothed.shape[1:]) // 512)
        preview = smoothed[z, ::step, ::step].compute()
    return {"result": out, "preview": preview}
```

Два писателя. **OME-Zarr** (по умолчанию) пишет блок за блоком,
параллельно, и строит пирамиду разрешений:

```python
def write_ome_zarr(arr, out, ctx):
    import zarr
    from ome_zarr.io import parse_url
    from ome_zarr.writer import write_image

    root = zarr.group(store=parse_url(str(out), mode="w").store)
    with WavuProgress(ctx):
        write_image(arr, group=root, axes="zyx", storage_options={"chunks": arr.chunksize})
```

**TIFF** идёт через **одного писателя**, плоскость за плоскостью, поэтому
он медленнее, не может работать параллельно, а результат — один большой
файл, который большинство просмотрщиков читают целиком. Здесь проверки
прогресса и отмены стоят в цикле:

```python
def write_tiff(arr, out, ctx):
    import tifffile

    cz = arr.chunksize[0]

    def planes():                                      # по одной пачке плоскостей за раз
        for z0 in range(0, arr.shape[0], cz):
            ctx.check_cancelled()
            ctx.progress(z0 / arr.shape[0])
            yield from arr[z0:z0 + cz].compute()

    tifffile.imwrite(out, planes(), shape=arr.shape, dtype=arr.dtype, bigtiff=True)
```

Каркас предполагает 3-D изображение `zyx`, у которого уровень полного
разрешения — `0`, как в OME-Zarr с одним изображением. Для 4-D или 5-D
данных поменяйте соответственно `axes` и срез для предпросмотра.

**Вызов.** Формат вывода — просто параметр, поэтому он входит в вызов и по
умолчанию равен OME-Zarr:

=== "Groovy (Fiji)"

    ```groovy
    def r = wavu.run(folder, "script",          // folder: папка скрипта
            [store: "D:/data/big.zarr", output_format: "ome-zarr"], [:])
    println r.files.result          // путь к новому OME-Zarr
    ```

=== "Python"

    ```python
    from wavu.client import Worker

    with Worker.start("path/to/stream-folder", on_log=print) as w:
        res = w.run("script", {"store": "D:/data/big.zarr", "output_format": "ome-zarr"})
        out = res.outputs["result"].value        # pathlib.Path
        preview = res.outputs["preview"].value   # маленький массив NumPy
    ```

`store` — обычный текстовый параметр, поэтому это должен быть путь,
который видит **воркер**. Wavu переводит пути входов для контейнера, но не
текстовые параметры: для воркера в контейнере вводите путь так, как его
видит контейнер.

**Как посмотреть результат.** Открывайте его лениво, чтобы читалась только
видимая часть: в napari — с читателем
[napari-ome-zarr](https://github.com/ome/napari-ome-zarr)
(`viewer.open(out, plugin="napari-ome-zarr")`), в Fiji — через
**File › Import › HDF5/N5/Zarr/OME-NGFF…** (плагины N5). Оговорка из начала
страницы остаётся в силе: просматривать можно, а анализировать всё целиком
внутри просмотрщика — нет.

## Когда не стоит делать это в Fiji или napari { #when-not-to-do-this-in-fiji-or-napari }

- **Свыше ~50 ГБ**, много файлов или много часов: запускайте тот же
  поблочный код как **пакетное задание** на рабочей станции, вообще без
  просмотрщика (`pixi run wavu run script.py --param store=D:/data/big.zarr`
  в терминале), на **HPC-кластере** (распределённый планировщик dask
  раскидывает блоки по многим машинам) или в **облаке** рядом с данными в
  объектном хранилище.
- **Когда результатом должен быть один TIFF** больше памяти: это возможно,
  но медленно; лучше выберите OME-Zarr и конвертируйте только нужную
  часть.

## Одним предложением

Для данных, которые не помещаются в память, дайте скрипту **путь** вместо
пикселей, пусть dask готовит OME-Zarr блок за блоком на нескольких плитах,
запишите результат рядом с входом и отправьте просмотрщику лишь
дегустационную тарелку, а сам Wavu просто передаёт путь туда и обратно.
